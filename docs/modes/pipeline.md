# Pipeline — 流水线模式

> **互见，主 timeline 内完成，不创建 sub-matter。**
> 链式传递：Leader 按步骤串行 @ 每步的执行者，每步的产出是下一步的输入。
> 像 Unix pipe：`step1 | step2 | step3`。

## 立场

流水线的价值在于分工正交——每步只做一件事，做完传走。
Leader 是传送带：读取上一步产出，@ 下一步执行者，附上上一步的结果作为输入。
所有步骤的产出都在同一条 timeline 里，彼此可见。

## 前提：步骤必须明确

Pipeline 无法自动推断步骤。开始前 Leader 必须知道步骤是什么：
- Brief 里写了步骤 → 直接用
- Brief 里没写 → Leader 自己规划，在 timeline 写出"我理解的 pipeline 是 A→B→C"
- 不确定 → **反问人，不猜**

## Leader 流程

```
[1] 写计划笔记
    读 Brief → 读 agent-cards 名册 → 确定步骤和每步执行者
    在 timeline 写出计划：
    「模式：pipeline
      步骤 1：[名称] → [agent] → [职责]
      步骤 2：[名称] → [agent] → [职责]
      步骤 3：[名称] → [agent] → [职责]
      下一步：@ 步骤 1 执行者。」

[2] @ 步骤 1 执行者
    「@<step1_uid> 你是流水线步骤 1/N：[步骤名]。
      你的职责：[描述]。
      输出要求：[格式]。
      完成后 @ 我。」

[3] 步骤 1 交回（@ 你 → 门铃唤醒）
    读 timeline 里的产出 → 检查质量
    更新计划笔记：「步骤 1 完成。下一步：@ 步骤 2。」

[4] @ 步骤 2 执行者，附上步骤 1 的产出
    「@<step2_uid> 你是流水线步骤 2/N：[步骤名]。
      上一步的产出（你的输入）：[粘贴或引用 timeline 位置]
      你的职责：[描述]。
      完成后 @ 我。」

[5] 重复直到所有步骤完成

[6] 汇总所有步骤的产出，写入 timeline，置 review 交回
```

**保活**：等待期间需定期 touch：
`octo-cli api POST /api/v1/matters/<id>/touch`

## 计划笔记示例

```
## 流水线计划
任务：竞品分析报告
步骤 1：信息搜集 → 执剑人 → 搜集 5 家竞品的公开数据
步骤 2：数据整理 → test2 → 整理为对比表格
步骤 3：分析结论 → 执剑人 → 基于表格写分析和建议
下一步：@ 执剑人开始步骤 1。
```

```
## 流水线进度（步骤 2 完成后）
步骤 1 ✓：搜集完成，见上方 timeline
步骤 2 ✓：表格已整理，见上方 timeline
步骤 3：待执行，@ 执剑人
```

## 参与者行为规范

当你作为某步骤的执行者时：

1. **只做你这步的事**：不要越界做下一步的工作
2. **基于输入工作**：如果 Leader 给了上一步的产出，以此为基础
3. **不修改上一步的产出**：只能基于它继续，不能改
4. **完整输出**：把产出直接写在 timeline 里
5. **写完 @ 领队**：这是显式信号，确保领队被唤醒

## 禁止

- 不得跳过步骤（即使你觉得某步没必要）
- 不得并行派步骤（pipeline 是严格串行的；并行用 split）
- 步骤执行者不得修改上一步的产出
