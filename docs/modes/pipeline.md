# Pipeline — 流水线模式

> 链式传递：A 完成后 Leader 手动将产出传给 B，B 完成后传给 C。
> 每一步有明确的输入、职责和输出。Leader 是传送带——读取上一步产出，派给下一步。

## 立场

流水线的价值在于**分工正交**——每一步只做一件事，做完传走。
像 Unix pipe：`step1 | step2 | step3`。
每步的输出是下一步的输入，中间不丢失、不变形。

## 前提：Brief 必须包含流转图

Pipeline 无法自动推断步骤。Brief 里必须写清楚：

```
## 流水线步骤
1. [步骤名] → [负责 agent] → [职责描述] → [输出物]
2. [步骤名] → [负责 agent] → [职责描述] → [输出物]
3. ...

## 步骤间依赖
step1 的输出是 step2 的输入。
step2 的输出是 step3 的输入。
```

如果 Brief 里没有这些信息，Leader 应该：
1. 先在 timeline 写出自己规划的步骤分解
2. 置 review 请人确认步骤分解是否合理
3. 人确认后再派子任务

## Leader 流程

```
[1] 读 Brief 中的流水线步骤定义

[2] 派第一步子任务
    octo-cli api POST /api/v1/matters --data '{
      "title":"[总任务名] — 步骤1: [步骤名]",
      "parent_matter_id":"<父id>",
      "step_id":"s1", "step_order":1,
      "leader_uid":"<步骤1 agent>",
      "description":"## 你在流水线中的位置\n步骤 1/N：[步骤名]\n\n## 你的职责\n[描述]\n\n## 输出要求\n[格式]"
    }'

[3] 第一步交回（门铃通知你）→ 读取产出
    octo-cli api GET /api/v1/matters/<子id>/timeline

[4] 派第二步子任务 — description 里粘贴上一步产出
    「## 上一步的产出（你的输入）\n[粘贴]\n\n## 你的职责\n[步骤2描述]」

[5] 重复直到所有步骤完成

[6] 汇总所有步骤的产出，写入父单 timeline，置 review 交回
```

**保活**：流水线可能持续较长时间，Leader 在等待各步交回时需定期 touch：
`octo-cli api POST /api/v1/matters/<父id>/touch`

## 步骤间的产出传递

- 每一步交回时，产出写在 timeline 里
- Leader 读取后，**原封不动或加工后**传给下一步
- 传递时在 description 里明确标注：「以下是上一步的产出，请基于此继续：」
- 不要让后续步骤自己去读前序步骤的 timeline（信息可能不完整）

## 每步子任务的 description 模板

```
## 你在流水线中的位置
步骤 {N}/{总步数}：{步骤名}

## 上一步的产出（你的输入）
{粘贴上一步的产出内容}

## 你的职责
{这一步需要做什么}

## 你的输出要求
{交回什么格式、什么内容}
```

## 禁止

- 不得跳过步骤（即使你觉得某步没必要）
- 不得并行派步骤（pipeline 是严格串行的；并行用 split 模式）
- 步骤负责人不得修改上一步的产出（只能基于它继续）
