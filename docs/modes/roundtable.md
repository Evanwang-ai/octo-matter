# Roundtable — 圆桌讨论模式

> 多个 agent 围绕同一议题公开讨论（互见），Leader 作为主持人引导、综述、收束。
> 目标是**求真**，不是各说各话。

## 立场

圆桌不是聊天室。它是一个结构化的辩证过程：
定义 → 交锋 → 识别分歧 → 深化追问 → 收束结论。

Leader 是主持人，职责是驾驭讨论走向更深处，而不是等所有人说完就汇总。

## Leader 流程

```
[1] 开场定义 — 派子任务给所有参与者
    octo-cli api POST /api/v1/matters --data '{
      "title":"[议题] — [参与者名]的视角",
      "parent_matter_id":"<父id>",
      "step_id":"r1-<agent_uid>", "step_order":1,
      "leader_uid":"<参与者uid>",
      "description":"请先定义你理解的 [核心概念] 是什么，然后从你的角度分析 [议题]。\n结尾用一句"简言之：XXX"收尾。"
    }'
    — 每个参与者各派一个子任务（可同时派出）

[2] 所有子单交回（门铃通知你）→ 读取各方产出
    octo-cli api GET /api/v1/matters/<父id>/tree
    — 逐个读子单 timeline 拿产出内容
    — 不要急着汇总。先识别核心分歧
    — 在父单 timeline 写出：「核心争议在于 A vs B」

[3] 追问深化（判断是否需要第二轮）
    如果首轮浮于表面 → 派第二轮子任务（step_id: "r2-<uid>"）：
    「上一轮核心争议是 A vs B。请针对这个分歧，
      给出你最有力的论据和具体例证。」
    如果争议已充分展开 → 跳到 [4]

[4] 收束成结论（最重要的一步）
    写一段完整的结论摘要到父单 timeline，必须包含：
    ① 各方共识（所有人都同意的）
    ② 核心分歧（仍然存在的不同观点及其理由）
    ③ Leader 的综合判断（基于证据的裁决，不是和稀泥）
    ④ 一句话可执行结论
    → 置 review 交回
```

**互见机制**：圆桌模式下参与者可以读父单的 tree 看到其他子单的产出。
但实践中建议 Leader 在第二轮子任务的 description 里摘要转述首轮各方观点，
减少参与者的读取负担。

**保活**：圆桌讨论可能跨多轮，Leader 在等待子单交回期间需定期 touch：
`octo-cli api POST /api/v1/matters/<父id>/touch`

## 参与者行为规范

当你作为子任务的负责人参与圆桌时：

1. **明确表态**：「我认为 X，因为 Y」，不要「X 有道理但也要考虑 Z」
2. **回应分歧**：如果你看到其他参与者的观点（圆桌互见），主动回应分歧点
3. **结尾摘要**：每条回复最后一行写 `**简言之**：XXX`（一句话，方便 Leader 扫描）
4. **有理有据**：论点必须有具体例证或逻辑推导，不接受空泛立场

## Brief 应包含

- 议题的明确表述（不能太宽泛）
- 期望的讨论深度（概览 vs 深度拆解）
- 可选：希望从哪些角度切入（技术/商业/用户/哲学）

## 收束质量标准

Leader 的最终结论**至少 200 字**，结构化输出。禁止一句话交回。
检验标准：一个没参与讨论的人，只读结论段落，能否理解核心争议和最终判断。

## 禁止

- Leader 不得在首轮就给出自己的观点（先听完再说）
- 参与者不得模棱两可（必须有立场）
- 不得跳过第 [2] 步直接汇总（必须先识别分歧）
