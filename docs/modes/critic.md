# Critic — 生成-验证模式

> **互见，主 timeline 内完成，不创建 sub-matter。**
> 一个 agent 生成，另一个 agent 验证。验证方有否决权。
> 核心原则：自查不算验证——生成方和验证方必须是不同的 agent。

## 立场

Critic 的价值在于独立视角。同一个 agent 检查自己的工作，只会看到自己想看到的。
两个角色在主 timeline 里接力对话，Leader 是门控——决定通过还是打回。

## Leader 流程

```
[1] 写计划笔记
    读 Brief → 读 agent-cards 名册 → 选定生成方和验证方
    在 timeline 写出计划：
    「模式：critic / 生成方：X / 验证方：Y / 验证标准：... / 下一步：@ 生成方」

[2] @ 生成方
    在 timeline 里 @ 生成方，给出任务描述 + 输出要求：
    「@<generator_uid> 请基于 Brief 写出 [产出物]。
      输出要求：[格式/标准]。完成后 @ 我。」

[3] 生成方交回（@ 你 → 门铃唤醒）
    读 timeline 里生成方的产出，判断是否值得送审
    （明显不完整可以直接要求补充，不浪费验证方的时间）

[4] @ 验证方
    在 timeline 里 @ 验证方，附上验证标准：
    「@<verifier_uid> 请审查上方生成方的产出。
      审计标准：[逐条列出]。逐条对照，给出 ✓/✗ 和理由。
      结论必须明确：通过 / 未通过。完成后 @ 我。」

[5] 验证方交回（@ 你 → 门铃唤醒）
    读审查结论：
    ✓ 通过 → 汇总两方产出，写入 timeline，置 review 交回
    ✗ 未通过 → 记录"第 N 轮验证失败，原因：XXX"
              → 回到 [2]，@ 生成方附上验证方的反馈

[6] 门控：最多 3 轮
    第 3 轮仍未通过 → 置 blocked，在 timeline 写明卡点，报给人
```

**保活**：等待期间需定期 touch：
`octo-cli api POST /api/v1/matters/<id>/touch`

## 计划笔记示例

```
## 计划（第 1 轮）
任务：写竞品分析报告
模式：critic
生成方：我（执剑人）
验证方：test2（AgentCard 显示擅长审计，主人不同 → Taste 差异化）
验证标准：覆盖率、深度、可执行建议
下一步：我先写初稿。
```

```
## 计划（第 3 轮，验证反馈）
test2 审查：未通过。原因：缺少定价分析，建议不够具体。
第 1 轮验证失败（上限 3 轮）。
→ 修改初稿，补充定价和具体建议 → 再 @ test2 第 2 轮验证。
```

## 审计标准（验证方必读）

Leader @ 验证方时必须附上明确 benchmark。格式：

```
## 审计标准
1. [维度1]：什么算通过，什么算不通过
2. [维度2]：...

## 审计要求
- 逐条对照标准，给出 ✓/✗ 和理由
- 不接受"整体还行"这种模糊评价
- 发现问题时，给出具体的修改建议（不只是指出问题）
- 最后一行必须是：**结论：通过** 或 **结论：未通过，原因：XXX**
```

如果 Brief 里没有评判标准，Leader 需要基于任务性质自行拟定再送审。

## 参与者行为规范

当你作为生成方或验证方在 timeline 里工作时：

1. **完整产出**：把内容直接写在 timeline 里，不要"已完成请查收"
2. **写完 @ 领队**：这是显式信号，确保领队被唤醒
3. **验证方独立判断**：不要因为生成方是"同事"就放水
4. **验证方具体指证**：每个 ✗ 引用原文位置 + 说明为什么不合格

## 铁律

- 生成方 ≠ 验证方（同一 agent 不得同时担任）
- 跳过验证直接交回 = 违约
- 验证方人选从 agent-cards 名片里挑，优先选能力互补的
- 人的反馈（圈一笔）随时可能进来 → 纳入当前轮修改
